# Player website and wiki (`docs/`, `scripts/tools/build-docs.py`)

The website docs: `website.md` (how the site is built: hosting, sources, the generator, the catalogue, guides and changelog data; start here), `website-pages.md` (what each page shows and does). How to update and publish it: `docs/dev/publishing-guide.md`.

## Hosting
- **GitHub Pages serves Live's `master` from the repository root** (Pages source `/`, not `/docs`): page addresses contain `docs/` (`https://ferlieloi.github.io/synergism-hypersynergy/docs/features.html`). The generated root `index.html` redirects the bare address to `docs/`; the root `.nojekyll` turns Jekyll off for the whole repository.
- **Links that rely on the root source:** the mod's Tools tab website button (`HSGlobal.General.modWebsiteUrl`, the bare address), the strategy editor's guide link (`modWebsiteUrl` + `docs/wiki/autosing-guide.html#making-or-editing-a-strategy`, `hs-autosing-strategy-modal.ts`), the README, the GitHub Wiki's pages, and the pictures taken from the mod's folder (`src/mod/resource/img/`: the category icons, "Sources and outputs", and the header's icon, `website-pages.md`, "Every page"). Switching Pages to `/docs` breaks them all.
- **Search engines are pointed to Live's site**, not the original repository's: every page, and the root redirect, has a canonical link to its address on the site (`site_url()`: `SITE` + its path, an index page as its folder), and `docs/sitemap.xml` lists every page (no dates: each run would differ), for Google Search Console. The repository being a fork of ahvonenj's let the original rank first.
- **The site is served from Live only.** Dev commits the data, never the generated pages (`docs/dev/releasing.md`, "Porting a change to Live"), so the pages in a Dev checkout lag the data and `--check` fails there.
- **The native GitHub Wiki** (`Ferlieloi/synergism-hypersynergy.wiki`, its own repository) holds only pages pointing to the website since 2026-11-04, written by hand there: one per category page plus Home, Mod-Features, the two references, sidebar and footer. Nothing in the repository generates them (not a generated Markdown wiki: it only duplicated the site).

## Sources and outputs
`build-docs.py` writes 29 files (Python, no dependency, no network). HTML pages start with a comment naming their source.

| Source | Generated from it |
|---|---|
| `docs/data/feature-catalogue.json` | `features.html`, `index.html` (home), `wiki/index.html`, `wiki/<category id>.html`, `FEATURES.md`, `FEATURE-AUDIT.md` |
| catalogue + `src/mod/resource/json/hs-settings.json` | `wiki/settings.html`; the header's settings count |
| `docs/data/guides/<category id>.md` | `wiki/<category id>-guide.html` |
| `docs/data/changelog.json` | `changelog.html` |
| `src/mod/class/hs-core/gds/hs-calculation-definition.ts` | `wiki/calculations.html` |
| `package.json` `version` | the header's "Guide for v…" on every page |
| `src/mod/class/hs-core/hs-global.ts` `modDiscordThreadUrl` | the Discord thread links (home page's Help, wiki index); not found = the run stops |
| the generator itself | `about.html`, `github.html`, root `index.html`, both `.nojekyll`, `sitemap.xml` (from the pages it built); every page text that isn't data (intros, the home page's steps, the changelog's introduction, the audit's "Reviewed distinctions" and "Verification limits") |

- **Read from the checkout**: version, settings and calculations come from the branch the generator runs on (why Dev's pages would show Dev's version and settings).
- **The site reads the mod's files, never the reverse:** the mod's build reads nothing in `docs/`, so site work can't break or change a mod release. What both show lives on the mod's side and the site points to it (settings, the mod's own icons in `src/mod/resource/img/`), with no copy.
- **Hand-written, served as they are:** `docs/css/original.css` (the original website's style, kept close to it), `docs/css/guide.css` (every adaptation; style changes go here), `docs/js/guide.js` (loaded on every page, acts only on the features page), `docs/js/changelog.js` (changelog page only), `docs/res/` (icons, GitHub logo, mod logo, `categories/` the category icons taken from the game, `guides/` and `features/` the screenshots). A change there reaches the site without regenerating. Category icons that are the mod's own (panel, heater) are the mod's files in `src/mod/resource/img/`, served from the repository root ("Hosting"): a change to one reaches the mod at its next release and the site at once.
- **Modes:** no option writes every file; `--check` compares without writing; `--validate` runs the catalogue, guide and changelog checks and the link check, building every page in memory, and writes nothing; `--changelog-only` writes or checks only `changelog.html` (after the catalogue checks); `--out DIR` writes to `DIR` (same layout, `DIR/docs/...`) instead of the checkout and copies the hand-written `css/`, `js/` and `res/` there, plus `src/mod/resource/img/` at `DIR/src/mod/resource/img/`, for a preview that leaves `docs/` untouched (not with `--check` or `--validate`). Outputs use LF.
- **Preview watcher** (`scripts/tools/watch-site.cjs`, `npm run site`): reruns `--out local/site` at each change of a source in the table above or of the hand-written files; `start-dev-server.bat` starts it with a server on port 8081 (no cache). Both are optional there: without Python, or with the port taken, the mod's build and server keep running.
- **`scripts/tools/prepare-image.cjs`** turns a screenshot into a site image (crop, scale down, WebP) through headless Chrome: `docs/dev/publishing-guide.md`, "Images".
- **`npm run screenshots`** (`scripts/tools/screenshots/`) takes the site's screenshots from an HS backup in the real game headless, and the Steam loader's window from its page with made-up data: `docs/dev/publishing-guide.md`, "Images".
- **Checks not run by `npm test`** (it runs only `*.cjs`): `python scripts/tests/test-changelog-validation.py` (changelog validation and credit rules), `python scripts/tests/test-build-docs.py` (the generator's logic: image sizes, heading ids, the guides' Markdown, links, settings' labels and defaults, version order, the calculation scrape, the output checks) and `node --check` on the two scripts.

## How the generator is organised
One Python file, no template engine: each page is an f-string.
- **Nothing is written until every output is built:** the checks run first (`validate_catalogue()`, which also parses every guide; `validate_changelog()` when the changelog page is built), every output goes into `OUTPUTS` (path → text) through `add()`, then `check_outputs()` checks them, then `main()` writes them all, compares them (`--check`) or writes them to `--out`. A refused input stops the run with no file written, so a new output goes through `add()` too, never straight to disk.
- **Every output's links are checked before writing** (`check_outputs()`), the generator's hand-written ones and `FEATURES.md`'s included: a relative `href`, `src` or Markdown link, or a full address of the site (`SITE`), names an output of the run or a file of the checkout, an anchor exists on a page of the run, no page uses an id twice. External links aren't (no network); with `--changelog-only`, anchors on the other pages aren't (on Dev the checked-in pages lag).
- **What the site's scripts look up exists** (full builds only): each id (`getElementById('…')`) and class (`querySelector('.…')`, `closest('.…')`) that `guide.js` or `changelog.js` names is on a page that loads it, so a rename on one side stops the run instead of breaking the search or the folds. Hence a script looks up the generator's elements by literal names, and its own elements (built by the script) not by id.
- **A page no output writes any more** (a category or guide removed or renamed), recognised by the generator's comment at its top: a build deletes it, `--check` reports it.
- **One frame for every page:** `page()` writes the head, header, tabs and footer around a page's body (`depth` sets the `../` prefix of pages in `wiki/`). The header and the tabs change there, once.
- **An entry is rendered twice:** `feature_html()` for the site (`compact=True` on the features page: details folded, first image as a miniature) and `feature_md()` for `FEATURES.md`. A change to how an entry is laid out goes in both.
- **The calculation reference is a text scrape** of `hs-calculation-definition.ts` (`calculationName`, `fnName`, `toolingSupport`, `supportsReduce`). The run stops when a `calculationName:` block doesn't give its name and `fnName` as double-quoted strings or a flag as `true` or `false` (an absent flag is false), when no entry is found, or when no entry has `supportsReduce: true`.

## Feature catalogue (`feature-catalogue.json`)
- **Top level:** `repository` (every repository, release, issue and source link: source links follow `blob/master/`), `audited_commit` (shown only in `FEATURE-AUDIT.md`), `branch` (not read), `categories` (in display order).
- **Category:** `id`, `title`, `color` (a CSS colour: the features page's category heading, and faded lines by the headings of its wiki page and guide), `intro`, `icon` (optional: a path from the repository root to a picture under `docs/res/` or `src/mod/resource/img/`, shown before the category's title on the home page, the wiki index, the features page and its wiki page), `sources` (repository paths, listed once in a small grey line at the end of its wiki page, above the footer, and under the intro of its `FEATURES.md` section; not on the features page), `features` (in display order).
- **Feature:** `id`, `title`, `summary`, `where`, `details` (list) are required; `limits` (list), `settings` (setting keys), `sources`, `images` (screenshots: `src` from `docs/`, `alt`, optional `caption`; a narrow one before the details, floating right of them, a wide one after them; also in `FEATURES.md`; on the features page the first one is also a miniature right of the title, whose click unfolds the details) are optional. An entry shows only its own `sources`, not its category's.
- **The generator refuses:** a category or feature id used twice, a missing required field, an unknown setting key, a setting of `hs-settings.json` no feature lists, a source path that isn't a file in the checkout, a missing icon or image, an icon outside `docs/res/` and `src/mod/resource/img/`, an image outside `docs/res/` or without `alt`, a key it doesn't know at any level (a misspelled optional one would be ignored), `details`, `limits`, `settings` or `sources` that isn't a list of strings, a setting's `platforms` value without a note in `PLATFORM_NOTES`. A setting listed by two features links to the last one on the settings page.
- **Ids name addresses; titles can change.** A category id names `wiki/<id>.html`, the GitHub Wiki's `Features-<id>` pointer page, its guide and the `?category=` filter; a feature id is its anchor on the features page, its wiki page and the settings page's links. `FEATURES.md` anchors features by title instead (GitHub's heading ids).
- **Plain text only**: every string is escaped on the site, so Markdown or HTML in a catalogue string shows as typed.

## Players' guides (`docs/data/guides/`)
- At most one per category, named by its id, first line `# Title`. Linked from its category on the features page and wiki page, and the wiki index ("Guides").
- **A Markdown subset** (the list: `docs/dev/publishing-guide.md`), anything else refused, inline too (italics, raw HTML, escapes, bare addresses, link titles, reference links, strikethrough), and what GitHub would read another way: a line right after a list item (it continues the item), a numbered list not starting at 1 (GitHub keeps the number), an image without a blank line above, an underlined heading, two headings with the same id (GitHub numbers the repeats), a link in a heading. So a guide renders the same on the site and on GitHub. Each heading gets the id GitHub would give it (lowercase, punctuation dropped, spaces to hyphens).
- **The installation guide (`getting-started.md`) is the one full install procedure**: every step, the Live/Dev switch, what to do when the mod doesn't load. The README keeps a short version per platform with the one-click links (Tampermonkey, the loader's install link, the releases page) and links the guide's Markdown file for the rest (it works on both repos at once; the site's page exists only once Live regenerates).
- **Alerts** (`> [!NOTE]`, TIP, IMPORTANT, WARNING, CAUTION): GitHub shows them with its icons; the site draws a box in the same colours with a matching icon. For what the reader must not miss, a few per guide: three in `autosing.md` (needs Tampermonkey or Steam, Save isn't final, copy the timings first).
- **Images:** alone on their line, path relative to the guide (so GitHub shows them too), rewritten for the site; `@<n>x` in the name sets the displayed size. One 850 px wide or less floats right of the text after it (placed right under its heading); headings start below a floating image, unless its path ends with `#past-headings` (GitHub ignores it): then the headings after it flow beside it, down to the next image, for one window that several sections describe. Rules: `docs/dev/publishing-guide.md`, "Images".
- **Annotated screenshots:** amber marks drawn by the screenshot scripts, a number or letter badge on each part the text names, an outline too around a group or a small unlabelled element (a labelled button gets its badge alone), an arrow where a jump needs showing. Numbers follow the steps in the order a player does them; letters when the same text is beside another image's numbers (the Heater's results beside its Inputs window). The text names a mark as ① or Ⓐ outside bold: on GitHub that character, on the site the same amber badge; in bold it stays the UI's own text (the Steam loader's "**① Locate game**"). Only where the text names a part of the image. A catalogue copy stays clean when its numbers belong to a guide.
- **A mod setting is written `**⚙ Label**`** (the label as the Settings tab shows it, a trailing "(…)" optional, case ignored): on GitHub a bold label with a gear, on the site a framed lilac label with a gear linking to its row on the settings page (hovering underlines the label only, its colour unchanged). The build stops when no panel setting, or more than one, has that label, so a renamed setting shows every guide line to update. Plain bold stays for buttons, tabs and windows. Not matched from plain bold: some panel "settings" are buttons or plain words ("📥 Import", "Ambrosia"), and the Heater's own Import button would have been marked.
- **Links: in-page anchors or full URLs.** A relative link to another page would point elsewhere from `docs/wiki/` than from the guide's file on GitHub. Images are the exception: the generator rewrites their path for the site.
- **A link to the site itself is a full URL to its address (`SITE`), made relative on the site**: no "opens elsewhere" icon, and the local preview stays local. It goes to a category's wiki page (a feature's id as anchor), a guide (a heading's id), the settings page (a setting's key) or the features page; the build stops on any other page, an unknown anchor, or an in-page anchor no heading has.
- **A feature explained elsewhere is linked at its first mention in a section** (`##`): its catalogue entry or its category's guide, whichever explains what the sentence needs. Not the guide's own feature; a button stays plain bold. Plain links, no mark: not an icon like the setting's gear, because bold already says "a named thing", nothing could check a feature's label, and feature names overlap button names ("Quick Import").
- **Renaming the "Making or editing a strategy" heading of `autosing.md` breaks the strategy editor's link** to it.

## Changelog data (`changelog.json`)
How the page shows it: `website-pages.md`, "Changelog page".
- **Top level:** `schema_version` 1, `methodology` (sentences, not displayed), `display_policy`, `contributor_profiles`, `entries`. `display_policy` is `all-records`; `released-only` would show only published and tagged versions, and a version linked from a catch-up but not shown would open from its link only.
- **Entry:** `id` (the anchor), `version`, `channel` (`original`, `live`, `dev`, `loader`), `repository`, `commit` and `previous_commit` (full hashes), `date` (UTC) with `date_kind` (`published`, `tag`, `commit`), `status` (`published`, `tagged`, `version-record`), `release_url` (or null), `sources` (label + URL), `changes` (`type`, `text`, `evidence` URLs not displayed), `notes`, `contributors`. Optional: `merges`, `aliases`, `earlier_changes` (shown folded under "Earlier changes recorded with this release", not on a catch-up), `included_version_records` (earlier version records of the same channel reviewed with this release; not displayed). Not read by the generator: `research_notes`, `contributor_range`. Any other key, at any level, is refused (a misspelled optional one would be ignored).
- **Every URL must be HTTPS on github.com**; the validation refuses any other, and any value outside the lists above.
- **`merges`** (a catch-up): `direction` `dev-to-live` on a Live entry or `live-to-dev` on a Dev entry, `from_entry_ids` (versions of the other channel, newest first), `partial_entry_ids` (some of those), `summary`, `commit`, `evidence`. The entry must credit a merger (`merge` role) and give nobody the `release` role.
- **Contributors:** `contributor_profiles` maps an id to `name`, `url` (or null), `aliases` and `identity_commits`; each entry's `contributors` gives the id, roles (`changes`, `release`, `merge`) and evidence commits.
- **`update-changelog-contributors.py`** computes credits from the local Git history: the human authors and co-authors of `previous_commit..commit` (loader: `synergism_modloader/` only), aliases merged through its own profile list, bots and coding agents left out, commits touching only version and build files counted as `release`. It skips catch-ups (credited by hand) and rewrites every other entry's credits: hand-reviewed credits on those are lost by a run without `--check`, which only reports the differences.
