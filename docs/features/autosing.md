# Autosing (`hs-modules/hs-autosing/`)

Autosing's place in the dialog queue: `docs/features/dialogs.md`.

Singularity automation driven by JSON "strategies". Defaults live in `resource/json/strategies/`, and validation is in `hs-modules/hs-autosing/hs-strategy-manager.ts`.
- **Speed comes first where it counts** (Shewchou, 2026-10-09). Autosing loops singularities for hours, so what runs inside its main loop, and the mod's background work and other features while it runs, must be as light as possible: no extra awaits, listeners or polling in the loop (plain boolean checks), and features may stay off during autosing for simplicity. Stop and pause latency doesn't matter (half a second later is fine), nor the "Finish & Stop" push at the end of a singularity (still maintained). No added complexity for negligible gains; prefer designs that survive game updates.
- **Runs never overlap.** A stopped chain sleeping past a restart used to wake up, see the shared `#autosingEnabled` flag `true` again (the new run's) and run alongside the new run. The chain promises (the main loop, and the final stage started by the antiquities observer) are kept in `#chains` (`#trackChain`), and `#startAutosing()` first waits for them (`#waitForPreviousChains`: after 10 s the start is cancelled with a warning and a notification), then runs `#isStartCancelled()`. Known limit, kept: an old chain can still do one action between its wake-up and its next flag check. A per-run object passed to every chain function with a check after every await (66 checks, 24 signatures), and throwing-wait or `AbortController` variants, were built and reverted (Shewchou: needlessly heavy; the smallest mechanism that removes the overlap wins).
- **The timer window's footer shows the patch state** (`#showPatchState` in `hs-autosingModal.ts`, right of "Module Version"): "Patched", "Patch incomplete", "Patch incomplete · slow" or "Not patched · slow", the parts found as its tooltip (set once per start). Each fast path only needs what it reads (`#hasStageFunc`, `#hasLivePlayer`, `#hasMaxChallenges`); "slow" means one of them falls back to the DOM, shown bold orange. A missing dialog hook, tack hook or export output is "incomplete" without "slow" (`docs/features/dialogs.md`). To see that state, a temporary `|| true` in the dialog hook's `if (!allFoundOnce)` in `patcher.js`, never committed.
- **A save load stops autosing** (`docs/features/gds.md`, "Every save load"): notification "Auto-Sing stopped: a save was loaded". A game reset (delete save) during autosing is left alone (same `reset = true` as a singularity). No login path loads a save (account forms, Discord / Patreon, account linking), so logging in never stops autosing.
- **The Exalt entry and exit run in one go** (`#enterAndLeaveExalt`, `#waitForExaltState`). The game sets `data-inside-singularity-challenge` on `<html>` inside the reset (`revealStuff()`, run by the reset's first tab change), so a `MutationObserver` on it fires right after the reset. With the dialogs answered at once (patcher hook), the entry, the exit and the tab restore happen in the task of the first click: no game tick runs inside the Exalt and Buildings is never painted. Patched players still read `player.insideSingularityChallenge`, and still poll it at each game tick: the attribute only wakes them earlier, and without it (a game update) the tick ends the wait as before. Bookmarklet players read the attribute. With debug logs on, a line gives the time taken and how many waits a tick ended (0 when the attribute did).
- **Autosing brings the player's tab back** (`#notePlayerTab` / `#showPlayerTab` in `hs-autosing.ts`). The tab is noted before each singularity, and before each DOM stage read (bookmarklet players: that read visits Settings > Stats). It is opened again right after the Exalt exit, and after each DOM stage read, through `HSSubtabMemory.openForPlayer` (subtab included). A locked tab (its button's computed `display` is `none`) is never clicked, the game would open the next unlocked one: the player stays where the game left them (Buildings), and that tab becomes the one to bring back until they open another. There is no return to a tab once it unlocks again: built as a setting and removed by Shewchou's choice (2026-10-11); don't propose it again.
- **Strategy actions window (`ui/hs-autosing-challenge-modal.ts`, rewritten 2026-10-29, commits 49ff3e58 fixes + 22c4fef3 rewrite).** The fields above the list come from one table, `FIELD_ROWS` (label, initial value, `shown` rule on the selected action and IF mode, `load` from a step): a new field is a row there plus a line in `#buildStep`. The dropdown's action numbers stay plain text (colouring only them needs a customizable select or a mod-built dropdown: Shewchou chose to leave it, 2026-10-29). Fields an action doesn't use are hidden, never greyed or disabled (Shewchou's choice); Stored C15 mode has its own Multiplier field and a text line instead of Value. ✎ loads every value of a step, so Update keeps the hidden ones. The window works on a deep copy (Cancel undoes IF target shifts). IF targets are step indices: adding/deleting a step shifts them (`#shiftJumpTargets`, a target at a deleted index stays), dragging a step does NOT: a target keeps its place in the list (Shewchou's choice 2026-10-29: making targets follow their step was tried and felt wrong in use, "I move it myself where I want"; don't propose it again). One drag routine (step, "Jump here" row, Add Here separator), drop place = number of steps whose middle is above the mouse, list redrawn on each change. In add mode a drag/delete keeps the typed fields. While dragging, the list auto-scrolls when the mouse is within 40 px of its top/bottom edge or past it (faster nearer the edge, up to 12 px per frame, a `requestAnimationFrame` loop on the last mouse position). ⧉ duplicates a step right after it, added as a new step there (targets shifted as for an add; a copied IF gets a new id and the original's target). Edit mode follows the edited step through a drag, a duplicate or a delete, renumbered, the typed fields kept (`#keepEditing`, by object identity; Shewchou's choice 2026-10-29, earlier a drag or delete left edit mode); deleting the edited step itself ends edit mode; Undo/Redo leave it (they swap the whole list). An IF's "→ step N" and a "Jump here" row's "(IF step N)" are links: a click flashes the other row violet, after scrolling the list just enough to show it plus the row past it, whatever that row is (the list's own `scrollTop`, never `scrollIntoView`; smooth). A row already fully in view: no scroll, even when its neighbour is cut off. Centring it was tried first and rejected by Shewchou (2026-10-29). An IF whose target is at or before its own step is a loop: "↺" on both rows. **Fields and closing (2026-10-29).** The Special Action dropdown has `<optgroup>`s by id ranges (`ACTION_GROUPS`; an action in none of them lands in "Other"). Families (`ACTION_FAMILIES`, Shewchou's choice 2026-10-29): 601–610 are one entry "601-610 - C1-C10 until no more completions" + Challenge # (1–10), 701–709 one entry "701-709 - Forge Auto-Buy Toggle" + a "Forge item" dropdown (names = label after "Forge Auto-Buy Toggle - "); editor only: a step still holds 601–610/701–709, so autosing, logs and the step list (long labels) are unchanged, no runtime cost. 211–214 kept as separate entries (Shewchou's choice). Groups: Exit and Ascend, Game actions (+ Forge), Condition, Challenges (211–215 + C1–C10), Ambrosia loadouts, Corruption level, AOAG and Autosing. A note under the dropdown explains C1–C10, naming the form's fields (a `shortLabel` for 601–610 was tried first, dropped with the families). The number fields the action shows are checked as they are typed (Shewchou's choice; `#checkFields` on every input/change and field show; `check` in `FIELD_ROWS`, a function of the context: Challenge # is 1–10 for the C1–C10 family): empty/non-number refused, Challenge # and If Challenge whole 1–15, Min Completions ≥ 0 (not 1: 0 = enter the challenge then wait inside, 123 steps in the default strategies), Corruption Level whole ≥ 0 (no more silent floor/clamp), waits and Max Time ≥ 0, Multiplier and IF Value any number; never corrected. Enter in a typed field (number inputs, comment; not a dropdown; not while composing) = Add/Update (Shewchou's choice 2026-10-29, after refusing it earlier as too hidden: the "?" box now lists it; Escape still refused). Every bad field turns red and the Add/Update button shows the first one's reason in its own box (red, one line) and refuses while any is bad: the agreed "red line under the button" was dropped for the no-resize rule (Shewchou's choice). Footer: "?" (a help box on hover: shortcuts, drag, IF targets, links, ↺, fixed time; `HELP_LINES`), Undo, Redo, then "Fixed time" (seconds, 3 decimals = ms precision, Shewchou's choice): every Wait before (measured from the end of the previous step at runtime, so they add up; IF steps included) plus Wait inside of standard challenges (only waited when the minimum is reached before Max Time) and 601–610 (always); nothing else in a step sleeps a fixed time; list run once, IF jumps not followed (Shewchou's choice). - **Corruption level (game 4.4.0).** One level (`player.corruptions.next`, used from the next ascension) instead of 8 corruptions. `HSAutosingCorruption` sets it through the game's `#corruptionLevelInput` + a `change` event (the game's `setNextCorruptionLevel`: synchronous, no dialog, no patch, the same for bookmarklet players), and reads it back from the live player, or from that input (the game writes the level it kept there). The game lowers a level above what the player can reach now, silently: 0 before C11 in the singularity, then `highestCleared` + 2 (+1 before singularity 2; `highestCleared` survives a singularity).
